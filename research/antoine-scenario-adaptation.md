# Porting Damn Vulnerable Drone attack scenarios to Antoine

## Research objective

Determine which of the existing MAVLink / ROS 2 exercises remain meaningful when the vehicle uses Antoine's Rust controller over the local Gazebo/NATS integration, and measure the security boundary of each ported scenario.

The research unit is an attack path, not a renamed protocol command: identify the old trust assumption, find the corresponding Antoine interface (if any), implement a bounded lab-only attempt, and judge success from independent evidence. A blocked attack is a useful result only when the expected security control and its evidence are recorded.

## System boundary

The default native profile runs one Antoine controller against an X500 in Gazebo. The optional `research/run-antoine-two-drone-flight.sh` runner starts 2–5 X500s, one independent Antoine controller and local demo authority per vehicle, and qualifies each vehicle against its own Gazebo pose and actuator evidence. Swarm behaviours (`lanes`, `column`, `vee`, `rendezvous`, `split`) are fixed per-vehicle waypoint plans generated before launch by `research/swarm_behavior.py`; the evaluator compares the final Gazebo poses against that plan and applies behaviour-specific gates. Non-lane plans use per-vehicle transit altitude layers and descend only at separated final slots. The planner also records a synchronized path-clearance estimate and rejects plans below a 1 m lab floor. These are static, pre-computed paths, not closed-loop formation control, consensus, or dynamic collision avoidance. At the default 8 m spacing, final slots are at least 5 m apart, matching S1's default minimum separation, but this profile does not start S1 or enforce its ORCA3D avoidance. An opt-in `ANTOINE_SWARM_MAVLINK=1` path starts one local bridge per callsign and checks per-vehicle MAVLink telemetry fan-out and system-ID isolation; it does not give the GCS control of the Gazebo swarm. Neither profile starts the legacy Flask/GCS/companion stack, uses the old Docker network or Wi-Fi, or exercises production Core authority. Antoine's per-run actuator and grant signatures are separate gates.

All experiments must use the local `./start.sh --mode antoine` profile, loopback NATS, throwaway keys, and the run-owned Gazebo process. No real aircraft, external broker, production key, or shared service is in scope.

## Priority experiments

1. **Waypoint Injection / GCS Spoofing:** copy a live local setpoint, mutate its target while retaining run/task/admission fields, and measure the grant binding, stop response, and independent motion. Then test wrong-run, wrong-vehicle, expired, and unsigned cases separately.
2. **GPS Spoofing / Replay:** use `research/run-antoine-sensor-tampering.sh` for the one-message signed-payload mutation. Extend only with distinct bounded stale and replay cases; battery and attitude inputs are not part of this active path.
3. **Packet Sniffing / Mission Extraction:** use `research/run-antoine-observation.sh` to inventory selected readable subjects and demonstrate what a client with access to the local broker can observe; redact key material and distinguish message visibility from actuation authority.
4. **Denial-of-Takeoff / Communication Link Flooding:** bounded waypoint mutation is implemented. Traffic disruption remains planned; before activation, add message, rate, and duration caps on a run-owned loopback broker and measure setpoint-to-command latency, state gaps, watchdog action, and neutralization.
5. **Flight Termination:** `research/run-antoine-early-revoke.sh` triggers one bounded signed revoke from inside the local test authority five seconds after its loop starts, then correlates controller acceptance, same-run neutral actuator output, and independent Gazebo pose. Qualification requires that it interrupt the mission before all legs complete. This measures local stop latency only; it does not claim landing or hardware safety.
6. **Firmware Modding / Decompile:** record source revision, binary digest, build features, and whether the runtime can detect a source/build mismatch.

## Evidence contract

Each experiment report should include scenario ID, run ID, source and asset revisions/digests, threat capability, attack start/stop, input count/rate, expected gate, observed allow/deny reason, actuator audit, controller stop reason, Gazebo pose timeline, and outcome. Never store private signing seeds in reports. A successful signature rejection alone does not prove no movement; correlate the rejection with actuator and independent pose evidence.

## Foundation review (2026-10-19)

The evidence chain is a local research harness, not a runtime attestation system. It depends on the Antoine checkout and Gazebo/simulation assets. Manifests hash public artifacts; optional Ed25519 sidecars authenticate possession of a local key when its public key is pinned. This does not prove which binary the operating system loaded. Every run binds relevant source/configuration fingerprints and runtime input digests before and after execution; the full checkout dirty-state digest remains contextual evidence, while documentation-only edits do not invalidate qualification. Incomplete or changed relevant inputs remain inconclusive. The checked-in scenario catalog is validated by one shared module and supplies UI state, launcher commands, and manifest coverage. Research console stop, GPS probe, flight launcher, and scenario shell runners compare process start time, process group, and PID before signaling. On Linux the shared signal helper binds delivery to a pidfd and rechecks identity after opening it; process-group termination is avoided. On macOS, Python has no pidfd equivalent, so the final `ps`-to-`kill` fallback remains non-atomic and an extremely narrow PID-reuse race is unresolved. GPS-forwarder executable/build-receipt provenance is included only when the run enables sensor forwarding.
